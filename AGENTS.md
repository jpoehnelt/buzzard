# Agent guide

Humans: see [README.md](README.md). This file lists the repo facts that the skills in `.claude/skills/` read.

## Layout

The workspace has six crates. Each crate depends only on crates listed above it.

| Crate | Owns |
| --- | --- |
| `crates/buzzard-rsrc` | The binary RSRC container parser, block decoders, the block diagram model (`BlockDiagram`, with constants, case selector tables, loop shift registers, tunnels and the recorded `Loss`es), the reader for `.llb` archives (`src/llb.rs`: `Llb::parse` lists the members, `Llb::read` gives the bytes of one; its module documentation holds the layout and what of it is not understood), and `builder::RsrcBuilder` and `builder::LlbBuilder` for synthetic test files |
| `crates/buzzard-lint` | Lint rules, dataflow checks, the project XML parser, the dependency graph, the external dependency report (`src/deps.rs`), SARIF, diagram rendering, the semantic diff, the state machine extraction, model and report (`src/verify`), archives as part of a workspace (`src/archive.rs`: member paths, reading a file or a member by its path, and the lookup of a member in an archive on disk), and the `ViInspector` backend trait |
| `crates/buzzard-ls` | The language server: engine, ordered update worker, file watching, and fuzzy symbol search |
| `crates/buzzard-mcp` | The Model Context Protocol server and its tools |
| `crates/buzzard-tdms` | The reader for TDMS measurement files: the segment index (`src/index.rs`), the value reads (`src/read.rs`), the public file, group and channel types (`src/file.rs`), scaling, the Parquet and CSV export (`src/export`, Parquet behind the `parquet` feature), and `build::FileBuilder` for synthetic test files. It depends on no other crate of the workspace. Its `README.md` lists what is supported |
| `crates/buzzard-cli` | The `buzzard` binary with the `check`, `inspect`, `deps`, `diff`, `verify`, `tdms`, `lsp`, and `mcp` subcommands. Each subcommand is one function in `src/main.rs`; `deps`, `diff` and `tdms` have a module each (`deps_cmd.rs`, `diff_cmd.rs`, `tdms_cmd.rs`) |

`editors/vscode` is a TypeScript VS Code extension over `buzzard lsp`. It is outside the Cargo workspace and has its own `npm` scripts (`lint`, `compile`, `test`, `package`).

`README.md` holds the durable docs: usage, rules, language server features, design goals, and current limitations. `RELEASING.md` holds the steps for publishing the crates to crates.io. The repo has no design records, ADRs, changelog, or changesets.

Each crate has its own `README.md`, `LICENSE` and `NOTICE`, because `cargo package` takes files from the crate's directory only. The `include` list in each `Cargo.toml` keeps a package to `src`, `examples` and those three files; tests and fixtures are not packaged. Its patterns start with `/`, because a pattern without one matches at any depth. The `LICENSE` files are copies of the root one, and only `crates/buzzard-rsrc/NOTICE` carries the LVKit and pylabview sections of the root `NOTICE` (the two generated tables in `src/blocks/heap`); `crates/buzzard-cli/tests/packaging.rs` holds them to that. The code examples in the crate READMEs are compiled as doctests (`ReadmeDoctests` at the end of each `src/lib.rs`).

## Checks

CI is `.github/workflows/ci.yml`. It runs every job on every pull request, merge group, and push to `main`, with no path filters. Run the same commands locally before a PR:

| CI job | Local command |
| --- | --- |
| `fmt` | `cargo fmt --all --check` |
| `lint` | `cargo +1.100.0 clippy --workspace --all-targets --locked -- -D warnings` and `RUSTDOCFLAGS="-D warnings" cargo +1.100.0 doc --workspace --no-deps --locked`. The toolchain is pinned in the `lint` job, not stable. |
| `test` | `cargo test --workspace --locked`, on Ubuntu, macOS, and Windows |
| `msrv` | `cargo +1.91 check --workspace --all-targets --locked`, using the `rust-version` in `Cargo.toml` |
| `deny` | `cargo deny check`, configured in `deny.toml`: RustSec advisories, licenses, wildcard versions and sources |
| `package` | `cargo package --workspace --locked`, with Cargo 1.90 or later. It builds every crate from its packaged files and publishes nothing. Delete `target/package` afterwards |
| `tdms-oracle` | `BUZZARD_TDMS_ORACLE=<python with npTDMS and pytest> BUZZARD_TDMS_ORACLE_STRICT=1 cargo test -p buzzard-tdms --test oracle`, on Ubuntu. Without the first variable the test passes without comparing anything |
| `ci` | None. It fails when any job above failed or was cancelled, and it is the job meant for branch protection. |

CI uses no secrets, so pull requests from forks run every job.

`.github/workflows/release.yml` is not a check. It publishes to crates.io and is started by hand only (`workflow_dispatch`); see `RELEASING.md`. Do not run `cargo publish` without `--dry-run`, create a tag, or add a trigger to that workflow: a published version is permanent, and the owner starts every release.

To run one integration test file, use `cargo test -p <crate> --test <file>`, for example `cargo test -p buzzard-lint --test rules`. To run unit tests by name, use `cargo test -p <crate> --lib <name>`.

Lints are clippy and rustdoc, both with `-D warnings`. The lint policy is `[workspace.lints]` in the root `Cargo.toml`, which every crate inherits with `[lints] workspace = true`; `clippy.toml` lets tests unwrap and print. To suppress one lint, put `#[expect(<lint>, reason = "...")]` on the smallest item that needs it. A bare `#[allow]` fails the `lint` job.

## Tests

- Unit tests sit beside the code in `#[cfg(test)] mod tests`, or in a `tests.rs` submodule such as `crates/buzzard-lint/src/project/tests.rs`. Integration tests live in `crates/<crate>/tests/`.
- The tests in `crates/buzzard-cli/tests/` run the built binary and write synthetic `.vi` files with the helpers in `tests/common/mod.rs`.
- No `.llb` archive with members is in the repository. The archive tests build theirs with `buzzard_rsrc::builder::LlbBuilder`: the unit tests in `crates/buzzard-rsrc/src/llb.rs` (the directory, the member reads, the size limits), `hostile_archives_never_panic` and its neighbours in `crates/buzzard-rsrc/tests/conformance.rs` (every truncation and every changed byte, also of the two real `.llb` fixtures, whose listings have `.archive.json` snapshots), `crates/buzzard-lint/tests/archive.rs` (members in a workspace, links, missing members, hostile names), `crates/buzzard-cli/tests/archive.rs` (every command on an archive and on a member path), `members_of_an_archive_are_shown_at_the_archive` in `crates/buzzard-cli/tests/lsp.rs`, and `tools_take_the_path_of_a_member_of_an_archive` in `crates/buzzard-mcp/tests/session.rs`. The layout the builder writes was read off an archive saved by LabVIEW 2017 that has no licence and is not in the repository; do not add a third-party archive without its source and licence.
- `crates/buzzard-rsrc/tests/conformance.rs` parses the real binaries in `tests/fixtures` and compares them with golden snapshots in `tests/snapshots`. To regenerate the snapshots, run `BUZZARD_BLESS=1 cargo test -p buzzard-rsrc --test conformance`, then review the diff before committing.
- `crates/buzzard-cli/tests/packaging.rs` compares each crate's `LICENSE` with the root one, checks what each crate's `NOTICE` holds, and checks the `include` list and `readme` of each `Cargo.toml`. After a change to the root `LICENSE` or `NOTICE`, copy it into the crates.
- Fixture files are byte-exact copies of upstream files (`.gitattributes`). Do not edit them. A new fixture records its source and licence, as `crates/buzzard-lint/tests/fixtures/project/README.md` does.
- `crates/buzzard-lint/tests/verify.rs` tests the state machine extraction on the real files in `tests/fixtures/verify` and on diagrams built by `tests/verify/build.rs`. Real classic enumeration machines have no licence and are not in the repo; `real_machines_outside_the_repository` and `damage_to_the_real_machines_proves_nothing_new` check them when `BUZZARD_FSM_SAMPLES` points at clones (run with `-- --ignored`).

- The TDMS tests write their files at test time with `buzzard_tdms::build::FileBuilder`, which keeps its own model of what each channel holds; the helpers are in `crates/buzzard-tdms/tests/common/mod.rs`. `tests/generated.rs` is the conformance cross product, the list of single-feature files (`feature_cases` in `tests/common/mod.rs`), the large reads and the index-file checks; `tests/property.rs` the property-based tests (proptest; a failing run prints its seed, and `PROPTEST_RNG_SEED=<seed>` repeats it), `tests/hostile.rs` the damaged and hostile input, `tests/export.rs` the exports, `tests/real.rs` the one real file in `tests/fixtures` (and, with `-- --ignored`, every file of a directory named by `BUZZARD_TDMS_SAMPLES`).
- `crates/buzzard-tdms/tests/oracle.rs` compares the reader with npTDMS, run as a separate program through `tests/oracle/dump.py`. Every disagreement is an entry in `KNOWN_DIFFERENCES` in that file with its reason; a disagreement that is not listed fails, and so does an entry that no longer occurs. Do not loosen the comparison to make a difference go away: fix the reader, or add an entry and repeat it in the table in `crates/buzzard-tdms/README.md`.
- npTDMS is LGPL-3.0. Do not read, copy or port its source, its tests or its fixtures into this repository. Use it only through `dump.py`, as a program.

Nine invariants have tests that enforce them:

- Output is byte-identical across runs, for example `check_output_is_byte_identical_across_runs` in `crates/buzzard-cli/tests/cli.rs` and `parsing_is_deterministic` in `crates/buzzard-rsrc/tests/conformance.rs`.
- Truncated or corrupted input returns an error and never panics, for example `hostile_input_never_panics` and `hostile_state_machine_fields_never_panic` in `crates/buzzard-rsrc/tests/conformance.rs`.
- A finding labelled `PROVEN` is never false: when anything about a diagram was lost or is not understood, the result is unknown, never a default. The diagram decoder records everything it skips or cannot trust as a `Loss` on the `Diagram` (`crates/buzzard-rsrc/src/diagram.rs`), including a field it cannot name (`Loss::Field`) and a heap whose byte stream is irregular (`Loss::Stream`, from `Heap::irregular`), and a diagram with a loss is not searched for classic state machines. `a_damaged_heap_never_adds_a_proven_finding` in `crates/buzzard-lint/tests/verify.rs` changes single bytes of the inflated heap of each fixture and checks both that no proven finding is added and that nothing is gone from a decoded diagram without a recorded loss; `BUZZARD_HEAP_DAMAGE_STEP` sets how many bytes it skips between two it changes (499 by default; 1 tries every byte and takes hours, so use `--release`). Its one exception is damage that leaves the structure of the diagram as it was and changes only a value (the test's `skeleton` function defines which fields are values): that is a complete diagram of another program, and proofs about it are printed and counted, not failed. `a_damaged_field_tag_in_a_real_file_proves_nothing` pins the case where a hidden field once read as a default. `every_loss_of_the_decoder_is_recorded` in `crates/buzzard-rsrc/tests/conformance.rs` covers each kind of loss. A decoder change that skips something new records a loss for it, and a decoder change that reads an absent field as a default first makes sure the field cannot be hiding.
- An `.llb` archive is untrusted, and a member name is data, never a path. Nothing is allocated from a declared count or size: the member count is checked against the bytes of the directory, and a member that declares more than `llb::MAX_MEMBER_BYTES`, or more than its zlib stream could hold, is refused before anything is inflated (`a_declared_size_of_gigabytes_is_refused_quickly` and its neighbours in `crates/buzzard-rsrc/src/llb.rs`). A member becomes a file of the workspace only under `<archive path>/<name>` and only if the name is one path component (`archive::is_addressable`); the path is made by `archive::member_path`, never by `Path::join`, which a name could redirect. `a_member_name_never_escapes_or_aliases_another_file` in `crates/buzzard-lint/tests/archive.rs` enforces it. An archive inside an archive is never opened. A directory layout the reader does not know (another version, bytes after the last entry, an entry without content) is an error on the archive, never a guess at its members.
- The state machine model over-approximates the diagram: anything the extraction cannot follow becomes `Successors::Unknown`, `Stop::Maybe` or an unknown initial state, never a guess. `an_unknowable_next_state_is_unknown_and_claims_nothing` and its neighbours in `crates/buzzard-lint/tests/verify.rs` enforce it. A change that makes the extraction follow something new documents the assumption in `crates/buzzard-lint/src/verify/extract.rs` and adds the case to those tests.

- The TDMS reader agrees with an independent statement of each file's contents: the generator's model (`every_shape_of_the_cross_product_reads_back` in `crates/buzzard-tdms/tests/generated.rs`, `random_segment_sequences_read_back` in `tests/property.rs`) and npTDMS (`the_reader_agrees_with_nptdms` in `tests/oracle.rs`). A change to how segments, metadata or raw data are interpreted keeps all three green; a new format feature gets a case in the generator first.
- The TDMS reader never panics, never hangs and never allocates more than a file accounts for. Sizes in a file are untrusted: arithmetic on them is checked, nothing is allocated from a declared count, and a channel is never longer than the bytes the file has for it. `a_file_cut_at_any_byte_gives_a_prefix_of_every_channel`, `any_single_damaged_byte_is_survived`, `seeded_random_damage_is_survived` and the directed cases in `crates/buzzard-tdms/tests/hostile.rs` enforce it; `a_file_cannot_make_the_index_grow_without_paying_for_it`, `walking_a_long_object_list_again_and_again_is_refused` and `a_million_empty_segments_cost_no_memory` bound the index and the time to build it. The crate has no `unsafe` code and does not memory-map; reads go through the `ReadAt` trait (`src/io.rs`).
- A truncated or unfinished TDMS file gives a prefix of every channel and an `Anomaly`, never invented values. Anything else that contradicts the format is an `Error` with a byte offset. A new way of recovering data adds an `Anomaly` variant and a row to the table in the crate's README. `anomalies_say_exactly_what_is_wrong` in `tests/hostile.rs` pins every field of every kind of anomaly; the command line's JSON prints them.
- An index file is believed only after its lead-ins and metadata were compared with the data file's, byte for byte, in every segment of a file of up to 64 segments and in evenly spaced segments of a longer one. `an_index_file_with_a_different_lead_in_is_rejected`, `an_index_file_with_other_metadata_is_not_believed` and `an_index_file_of_a_long_file_is_checked_in_evenly_spaced_segments` in `tests/generated.rs` pin where that line is. Do not make the reader believe more of an index file than they allow.

## Contracts

These are the surfaces that users and other tools depend on. Check them when you judge a change's blast radius.

- Rule codes (`BZ000` and up) are defined in `RULES` in `crates/buzzard-lint/src/rules.rs`. Users pass them to `--ignore`, and SARIF output uses them as `ruleId`. Renaming a code breaks user configs and code scanning history. `BZ201`, `BZ202` and `BZ203` are the state machine findings; their messages end in `(proven)`, `(structural, not proven)` or `(heuristic, not proven)`, and `README.md` states what each means. Do not label a finding proven unless it follows from the over-approximating model. A fact about the wiring that says nothing about what runs is structural.
- A member of an `.llb` archive is named by a member path: the path of the archive, a separator, and the member's name (`lib/util.llb/Init.vi`). `check`, `verify`, `deps`, `inspect`, both sides of `diff`, and every MCP tool that takes a file accept one, and the human and JSON output of `check`, `verify` and `deps` and the MCP results print members that way. Users pass these paths in scripts, so the shape is a contract. A member path whose archive is on disk and does not hold the member is a path that does not exist (status 2 for `check`, `verify` and `deps`); one side of `diff` that names such a member is an added or deleted file. SARIF and the language server never show a member path as a location: a finding about a member is located at the `.llb` file with the member's name at the start of its message (`Diagnostic::on_disk`), and SARIF adds a `logicalLocations` entry (`name`, `fullyQualifiedName`, `kind` `member`). Code-scanning history and editor clients depend on that.
- `buzzard inspect` on an `.llb` file prints the archive's directory: Markdown, or JSON with `kind` (`library`), `file_type` (`LVAR`), `members` (each with `name`, `id`, `file_type`, `kind`, `version`, `storage` of `stored`, `zlib` or `legacy`, `stored_size`, `size`), `unlisted`, and `problems` when there are any. `svg`, `dot` and `mermaid` exit 2 and ask for a member. An archive whose directory cannot be read exits 2.
- `buzzard check` prints `--format human`, `json`, or `sarif`. `buzzard inspect` prints `--format markdown`, `json`, `svg`, `dot`, or `mermaid`. `buzzard diff` prints `--format text`, `markdown`, or `json`, and exits 0 when the two files are the same, 1 when they differ, and 2 on an error. `buzzard verify` prints `--format text`, `json`, or `dot`, and exits 0 when it has no findings, 1 when it has any (of any label), and 2 on an error such as a path that does not exist; a file it cannot parse, and a file whose block diagram did not decode completely, is listed and does not change the status. Each finding carries a label (`Confidence` in `crates/buzzard-lint/src/verify/mod.rs`): the text report prints `PROVEN`, `STRUCTURAL` or `HEURISTIC`, and the JSON field `confidence` holds `proven`, `structural` or `heuristic`. Tools that read the report depend on those words.
- `buzzard deps` prints `--format text`, `json`, or `markdown`, and exits 0 whatever the report holds, or 2 on an error: a path that does not exist, or a `--root` that cannot be used (not `NAME=DIR`, a name that is not a root's, a directory that does not exist or is not one, or one root given two different directories). A `--root` that no link is under is not an error: it is listed in `unused_roots` and warned about on stderr. A file it cannot parse is listed under `unparsed` and does not change the status. The JSON is the serialized form of `DepsReport` (`crates/buzzard-lint/src/deps.rs`): `files`, `roots` (each with `root`, optional `directory`, and `packages` of `name` and `targets`; a target has `path`, `status` and `referrers`), `absolute` and `missing` (entries of `target` and `referrers`), `unparsed` (entries of `path` and `message`), and `unused_roots`, left out when empty. `status` is `found`, `missing` or `unchecked` (`Status` in the same file); the text and Markdown reports print the same words. A target is `unchecked` unless `--root` gave its root a directory: do not report a file as found or missing without a look at the disk. A target inside an `.llb` is `found` only if the archive on disk holds a member of that name, `missing` if the archive is there and does not, and `unchecked` if the archive cannot be read (`archive::Archives`, which `BZ006` and the missing relative links use too). The look ignores letter case and tries the legacy code page readings before it says `missing`. Stored paths and package names that differ only in letter case are one target and one package, and a member URL is filed as the `LvPath` it spells, so that a VI and a project file naming one location give one entry. The package rule is `deps::package`; `README.md` states it, and tools that group by package depend on it. Whether a relative link is missing is decided by `DependencyGraph::link_target`, `DependencyGraph::parent_target` and `rules::member_is_missing`, which the graph and `BZ006` use too, so the report and `check` never disagree.
- The JSON of `buzzard inspect` and `buzzard verify` is the serialized form of `BlockDiagram` (`crates/buzzard-rsrc/src/diagram.rs`) and `Verified` (`crates/buzzard-lint/src/verify/report.rs`). Optional diagram fields (`constant`, `numeric`, `tunnel`, `param`, `selector`, `loop_info`, `losses`) are left out when absent or empty.
- `buzzard mcp` serves the tools listed in `README.md` over stdio; `NAMES` in `crates/buzzard-mcp/src/tools.rs` is the list. Agents depend on the tool names and their argument schemas. `buzzard_verify` takes `paths[]` and `format?` (`text`, `json`, `dot`) and returns what `buzzard verify` prints; unlike the CLI, findings do not make it an error result. `buzzard_deps` takes `paths[]`, `format?` (`text`, `json`, `markdown`), `roots?` (an object of root name to directory, or a list of `NAME=DIR` strings) `detail?` (`packages`, `files`) and `refresh?`. With `detail` `files` it returns what `buzzard deps` prints, with the JSON as structured content; with `packages`, the default, it returns counts per package and per link (`deps::Overview`), because the full report of a large workspace is megabytes.
- `check` exits 0 when it finds no problems and 1 when it finds any, unless `--exit-zero` is set. A file it cannot parse is a `BZ000` problem, not an error; so is a member of an archive that cannot be read (on its member path), and an archive whose directory cannot be read or that has a member whose name is not a file name (on the `.llb` file). It exits 2 for an unknown `--ignore` code or a path that does not exist. `inspect` exits 2 when it cannot read the file. CI pipelines gate on these statuses.
- The language server implements the standard methods listed in `README.md`, plus the custom requests `buzzard/inspect` and `buzzard/exportAst` in `crates/buzzard-ls/src/server.rs`. Editor clients depend on their JSON shape.
- `buzzard tdms info <file>` prints `--format text` or `json` and exits 0, or 2 when the file cannot be opened; anomalies such as a truncated last segment are part of the report and do not change the status. The JSON is the `InfoJson` struct in `crates/buzzard-cli/src/tdms_cmd.rs`: `file`, `size`, `segments`, `versions`, `index` (`data_file`, `index_file` or `index_file_rejected`), `anomalies` (each with `kind` from `Anomaly::kind` and `message`), `properties`, and `groups` with their `channels` (`name`, `path`, `type`, `length`, optional `unit`, `waveform`, `scalers`, `scaling`, and `properties`). Type names are those of `DataType::name`. Tools that read the report depend on these names.
- `buzzard tdms export <file> --out <path> [--channels ...] [--format parquet|csv] [--compression snappy|none] [--raw] [--threads N]` exits 0, or 2 on any error (unreadable file, unknown channel or group name, a write failure), and leaves no output file behind on an error. Columns are named `group/channel` (`.re` and `.im` for complex channels) with a leading `time_s` when the channels share their waveform timing. The Parquet key-value metadata keys (`tdms.file.*`, `tdms.group.*`, `tdms.channel.*`, `buzzard.channel.*`, `buzzard.time.*`, `buzzard.tdms.version`) are listed in `crates/buzzard-tdms/src/export/parquet.rs`; analytics pipelines depend on the column names and on these keys. The same input and options give the same bytes (`export_writes_parquet_by_default_and_is_deterministic` in `crates/buzzard-cli/tests/tdms.rs`).
- The public API of `buzzard-tdms` (`TdmsFile`, `Group`, `Channel`, `OpenOptions`, `Error`, `Anomaly`, `export`) is what other programs build on. `Error`, `Anomaly`, `DataType`, `PropertyValue`, `Column`, `Scaling` and `export::parquet::Compression` are `#[non_exhaustive]`.
- Once released on crates.io, the public APIs of `buzzard-tdms` and `buzzard-rsrc` are published surfaces: a breaking change needs a new minor version while the crates are at 0.x, and a published version cannot be changed. That includes the builders (`buzzard_tdms::build`, `buzzard_rsrc::builder`), which are public test support. In `buzzard-rsrc`, `RsrcError`, `Loss`, `DataType`, `RefKind`, `NumericType`, `Value`, `SelectorKind`, `TunnelMode` and `llb::Storage` are `#[non_exhaustive]`; `SelectorMatch`, `PathKind`, `FileKind` and `Direction` are matched exhaustively by `buzzard-lint` and are not. `buzzard-lint`, `buzzard-ls` and `buzzard-mcp` are published only so that `cargo install buzzard-cli` works; their READMEs say that their API may change in any release.
- The crate names on crates.io (`buzzard-rsrc`, `buzzard-lint`, `buzzard-ls`, `buzzard-mcp`, `buzzard-tdms`, `buzzard-cli`) and the binary name `buzzard` are permanent once published.
- Input formats are binary RSRC files (the extensions in `RSRC_EXTENSIONS` in `crates/buzzard-rsrc/src/lib.rs`), `.llb` archives of them (`LLB_EXTENSION`) and project XML files (`.lvproj`, `.lvlib`, `.lvclass`), saved by the LabVIEW IDE, and TDMS measurement files (`.tdms`, with an optional `.tdms_index` file beside them) written by data-acquisition software.

## Running and measuring

- Run the CLI with `cargo run -p buzzard-cli -- check <path>` or `cargo run -p buzzard-cli -- inspect <file>`. Run the language server over stdio with `cargo run -p buzzard-cli -- lsp`. There are no ports, services, seed data, or credentials, so instances in separate worktrees do not collide.
- The fixtures under `crates/buzzard-rsrc/tests/fixtures` and `crates/buzzard-lint/tests/fixtures/project` are real inputs to run against.
- `README.md` claims that a release build checks 1,300 real files from three open-source projects in about 0.2 s on four cores. That corpus is not in the repo; the README names the three projects. Time `target/release/buzzard check <dir>` after `cargo build --release`. To check that the parser accepts every file in a directory, run `cargo run --release --example corpus -- <dir>`.

- `buzzard tdms info <file>` and `buzzard tdms export <file> --out <path>` run against `crates/buzzard-tdms/tests/fixtures/zenodo-7758683/waveforms-point21.tdms`, the one real TDMS file in the repo.
- The crate's `README.md` gives the TDMS reader's speed on generated files of about 400 MB. To measure it again, run `tools/tdms-bench.sh [SIZE_MB] [DIR]`; it builds the `tdms_bench` example in release mode, writes each file under `target/tdms-bench` by default, and deletes it afterwards. Update the table in the README when a change moves the numbers.

## Commits and pull requests

- Commit subjects and PR titles are short imperative sentences in sentence case, without Conventional Commit prefixes. For example: "Add dataflow rules BZ101 and BZ102 and block diagram export".
- There is no PR template. Impact statements go in the PR description. Its readers are LabVIEW developers who run `buzzard check` in CI or use the language server in an editor.
